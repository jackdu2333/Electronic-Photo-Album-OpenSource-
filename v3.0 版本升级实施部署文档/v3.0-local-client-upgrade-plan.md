# v3.0 Local Client Edition 电子相册本地独立客户端升级方案

## 1. 核心定位

本次 v3.0 升级的目标，是把现有云端/服务器型电子相册升级为 **多端独立本地客户端**。

最终形态：

- 桌面端、iPhone、iPad 各自独立运行。
- 每台设备只引用本设备上的本地照片。
- 不依赖云端部署。
- 不把电脑作为家庭中心服务器。
- 不做多设备之间的照片同步。
- 不默认复制原图。

本次推荐技术路线：

**共享 Web Core + 平台原生本地照片访问层。**

也就是说：

- 现有 Flask / HTML / JavaScript 继续作为展示和管理核心。
- 桌面端用本地客户端壳启动本地服务，并选择本机相册文件夹。
- iPhone / iPad 用原生壳承载 Web Core，并通过 PhotoKit 读取本机相册。
- 平台差异集中在照片源适配层，不重写现有相框主题和推荐体验。

## 2. 总体架构

### 2.1 Web Core 展示内核

复用现有能力：

- 首页幻灯片展示
- 多主题展示
- 智能推荐算法
- 标签、日期、便签
- 深海打捞
- 管理后台
- 上传导入能力作为兼容能力保留

需要改造：

- 所有照片访问不能再假设来自 `/static/photos/`。
- 前端不再自行拼接静态照片路径。
- 前端统一使用后端返回的 `display_url`。
- 旧接口可以保留，但底层数据来源改为统一照片源服务。

### 2.2 Photo Source Adapter 照片源适配层

不同平台各自实现照片来源。

桌面端：

- 用户选择一个或多个本地相册文件夹。
- 扫描本地图片。
- 生成稳定 photo id。
- 原图只读引用。
- 删除操作默认只删除电子相册索引，不删除原图。

iPhone / iPad：

- 用户授权系统相册。
- 使用 PhotoKit / PhotosPicker 获取照片。
- 保存 `PHAsset.localIdentifier`。
- 原图留在系统照片库。
- App 只保存索引、标签、便签和必要缓存。

### 2.3 Local Data Store 本地数据层

统一用 SQLite 存储：

- 照片索引
- 本地来源信息
- 标签
- 日期
- 便签
- 展示次数
- 缩略图缓存记录
- 缺失照片状态

建议逐步把当前 JSON 元数据并入 SQLite，减少多端适配成本。

## 3. 关键数据模型

建议新增或改造 `photos` 表。

核心字段：

```text
id              本地唯一 photo id
source_type     desktop_folder / ios_photokit / imported_copy
source_ref      原始引用，桌面为本地路径引用，iOS 为 PHAsset localIdentifier
display_url     前端展示 URL
date            拍摄日期
month           拍摄月份
tags            标签
note_title      便签标题
note_body       便签正文
width           图片宽度
height          图片高度
weight          推荐权重
view_count      展示次数
missing         原图是否缺失
created_at      入库时间
updated_at      更新时间
```

安全要求：

- 桌面端不要把绝对路径直接暴露给前端。
- 前端只使用 `/api/photos/{id}/image` 这类受控 URL。
- 后端根据 `id` 查询真实路径，再做边界校验和文件返回。

## 4. API 设计

### 4.1 照片列表

```http
GET /api/photos
```

返回示例：

```json
[
  {
    "id": "desktop_abcd1234",
    "display_url": "/api/photos/desktop_abcd1234/image",
    "date": "2024-05-01",
    "month": 5,
    "tags": "旅行,宝宝",
    "note_title": "",
    "note_body": "",
    "source_type": "desktop_folder",
    "missing": false
  }
]
```

这个接口作为新照片数据源。旧的 `/api/images` 和 `/api/all_photos` 可以保留，但内部应改为调用新照片服务。

### 4.2 获取图片

```http
GET /api/photos/<photo_id>/image
```

桌面端：

- 校验 photo id 是否存在。
- 校验路径仍在用户授权文件夹内。
- 返回本地图片文件。

iPhone / iPad：

- 由原生层拦截或桥接请求。
- 根据 `PHAsset.localIdentifier` 读取图片数据。

### 4.3 更新元数据

```http
POST /api/photos/<photo_id>/metadata
```

更新内容：

- 日期
- 标签
- 便签标题
- 便签正文

要求：

- 不修改原图 EXIF。
- 只更新电子相册本地数据库。

### 4.4 移除照片引用

```http
DELETE /api/photos/<photo_id>
```

默认行为：

**只从电子相册中移除引用，不删除原文件。**

如果后续支持“删除原图”，必须作为高级选项，并增加二次确认。

### 4.5 扫描本地照片源

```http
POST /api/photo-sources/rescan
```

桌面端使用。

行为：

- 扫描授权文件夹。
- 新增照片入库。
- 标记已经不存在的照片为 `missing=true`。
- 不主动删除数据库记录。

## 5. 桌面端方案

### 5.1 技术建议

推荐优先级：

1. Tauri + 本地 Flask 服务
2. Electron + 本地 Flask 服务
3. PyInstaller + 浏览器窗口

建议优先选 **Tauri**：

- 包体小。
- 适合本地客户端。
- Mac / Windows 支持好。
- WebView 可以承载现有前端。
- 原生层可以负责文件夹选择、系统托盘、启动本地服务等能力。

### 5.2 桌面端启动流程

1. 用户打开 App。
2. Tauri 启动本地 Flask 服务，监听 `127.0.0.1` 随机端口。
3. WebView 打开本地地址。
4. 首次进入显示“选择本地相册文件夹”。
5. 用户选择文件夹。
6. App 保存授权目录。
7. 扫描照片，写入 SQLite。
8. 进入相框展示页面。

### 5.3 桌面端 MVP 功能

必须有：

- 选择本地相册文件夹。
- 支持多个文件夹。
- 手动重新扫描。
- 展示本地照片。
- 编辑标签、日期、便签。
- 移除照片引用。
- 缺失照片提示。
- 断网可用。

暂不做：

- 自动监听文件夹变化。
- 云同步。
- 人脸识别。
- AI 自动打标签。
- 删除原图。

## 6. iPhone / iPad 方案

### 6.1 技术建议

推荐：

**Swift / SwiftUI 原生壳 + WKWebView + PhotoKit。**

原因：

- iOS 照片权限必须走系统能力。
- PhotoKit 访问体验更稳定。
- WKWebView 可以复用现有 Web Core。
- iPad 横屏相框体验可以做原生增强。

### 6.2 iOS / iPadOS 启动流程

1. 用户打开 App。
2. App 请求照片权限。
3. 用户选择照片或相册。
4. App 保存 `PHAsset.localIdentifier`。
5. 本地 SQLite 建立索引。
6. WKWebView 打开本地 Web Core。
7. Web Core 请求照片时，通过 bridge 获取本机照片数据。

### 6.3 iOS / iPadOS MVP 功能

必须有：

- 系统相册授权。
- 选择照片加入电子相册。
- 本地展示。
- 本地推荐播放。
- 编辑标签、日期、便签。
- 撤销权限后的提示。
- 飞行模式可用。

暂不做：

- iCloud 跨设备同步。
- 后台自动扫描全部相册。
- 与桌面端互传。
- Android 同步升级。

## 7. 前端改造重点

当前很多地方直接拼接：

```javascript
/static/photos/${photo.url}
```

需要统一改为：

```javascript
photo.display_url
```

改造范围：

- 首页主脚本
- 独立主题页
- 管理后台
- 瀑布流主题
- 画廊主题
- 拍立得主题
- 删除接口调用
- 元数据编辑接口调用

目标：

**前端完全不知道照片来自哪里，只消费统一照片对象。**

## 9. 风险和取舍

### 9.1 iOS 不能像桌面一样直接扫文件夹

解决：

- iOS 只走系统照片库授权。
- 不设计“任意文件夹扫描”。
- 用 `PHAsset.localIdentifier` 做引用。

### 9.2 现有前端硬编码静态图片路径较多

解决：

- 第一优先级统一 `display_url`。
- 旧接口保留，新接口替换底层。
- 分主题逐个改，避免一次性重构失控。

### 9.3 桌面端本地文件权限和路径安全

解决：

- 只允许访问用户授权目录。
- photo id 不暴露真实路径。
- 返回图片前做路径边界校验。
- 删除默认只删索引。

### 9.4 多端代码复用边界不清

解决：

- Web Core 只负责 UI 和业务交互。
- 原生壳只负责平台能力。
- 照片源接口作为唯一边界。
